# Workspace contract

All research skills read and write these paths. Paths are relative to the workspace root unless they start with `poc/<idea-id>/`.

## Layout

```text
company-context.md                 # shared, written by the user
research-map.md                    # shared, built by research-map with the user: problem formulations, anchors, near-misses
scouting/calibration.md            # shared, rules from user overrules (source-scout); read by scout, alignment and critic
poc/<idea-id>/
  .poc/                            # workflow state, written only by scripts/poc_state.py
    pipeline.json                  #   stage graph for this idea
    state.json                     #   verdicts, fingerprints, approvals
    events.jsonl                   #   append-only history (start/complete/approve/reopen/abort)
  STATUS.md                        # generated state table + human decisions and notes
  reviews/<stage>-<run>.md         # stage-critic reviews, one per round; never edited by the writer
  sources/<source-id>/
    digest.md                      # stage 1
    source.*                       # optional local copy (pdf, html, notes)
  sources/sources.md                # optional: paper URLs/versions to digest (a digest input)
  ideas/
    alignment.md                   # stage 2
    proposal.md                    # stage 3
  experiments/
    plan.md                        # stage 4, written before any code
    reported_targets.json             # numbers to reproduce, from digest
    reproduction.md                # stage 4 verdict
    extension.md                   # stage 5 report
    code/                          # harness (or a git submodule / link to it)
    configs/                       # one config per run group
  results/
    runs.jsonl                     # append-only run records
    improvements.md                # stage 6, generated by result-plots
    summary.md                     # stage 6
  figures/                         # stage 6, .svg + .png + .csv
    src/                           # plotting source for custom figures
  deck/                            # stage 7, insight-ppt output
```

`sources/INDEX.md` (optional): one row per digested paper when reading a batch.

`source-id` format: `<author-or-org><year>-<short-title>`, e.g. `leis2018-learned-index`, `duckdb2026-external-agg`. Sources can be papers, open-source projects or technical blog posts; the digest records the type and evidence level.

## Stage 1 — `digest.md`

Required sections, in order:

1. **Citation**: title, authors or org, type (paper / open-source / blog post), venue or project and date, evidence level, links to the source, code and artifacts.
2. **Problem**: what problem it solves and why existing methods fall short (per the paper).
3. **Key insight**: one sentence.
3b. **Purpose–mechanism and canonical formulation** [TM-2, TM-5]: purpose (what it is for), mechanism (how, one line), and the formulation — given inputs, produce outputs, optimising objective, subject to constraints, in regime — in generic terms; plus adjacent fields where the same formulation appears. This is the block idea-alignment matches on.
4. **Mechanism**: how it works, detailed enough to reimplement; include key equations or pseudocode.
5. **Assumptions**: explicit and implicit (data distribution, workload, hardware, scale).
6. **Limitations and weak spots**: stated by the authors, plus `[inference]` items. Extensions come from here.
7. **Benchmark protocol**: datasets (version, split, preprocessing), workloads or queries, metrics with exact definitions, baselines with versions, hyperparameters and tuning procedure, number of seeds or repetitions, hardware, software versions, time or compute budget.
8. **Reported results**: the main table(s) copied with table or figure numbers, including variance if reported.
9. **Protocol gaps**: anything in section 7 the paper does not specify.

## Stage 2 — `alignment.md`

For each candidate match: the **relevance chain** (paper formulation, research-map sub-problem id, shared structure, transfer distance, bridging concept, what transfers as-is, what must change), the **ground point** in Toulmin form (claim, grounds, warrant, qualifier, rebuttal), the assumption table (holds / breaks / unknown), which company data or system is involved, and a score of 1–5 for impact, feasibility, effort (5 = low effort), risk (5 = low risk) and strategic fit, each with one line of rationale citing `company-context.md` or `research-map.md`. Then: the ranked list (pairwise-settled when > 3), a *Direction synthesis* section when several digests were read, rejected matches with reasons, and the user's selection. A match without a shared-structure line is invalid.

## Stage 3 — `proposal.md`

0. **Heilmeier catechism** [TM-7]: the eight answers, jargon-free.
1. **Extension**: what changes relative to the paper, and why it should help in the company setting.
2. **Novelty check**: search queries and sources used, with dates; the 3–10 closest prior works, each with a difference statement; an overall verdict of `novel`, `incremental` or `already done`.
3. **Hypothesis**: "Method X improves metric M by ≥ Y over baseline Z on benchmark B under condition C."
4. **Falsification**: the result that would reject the hypothesis.
5. **Experiments**: main comparison, ablations, sensitivity studies, datasets, seeds, and estimated compute.
6. **Company relevance**: which result would matter to the business and why.

## Stage 4 — `experiments/reported_targets.json`

```json
[
  {"method": "baseline-name", "dataset": "ds", "split": "test", "metric": "recall@10",
   "value": 0.912, "higher_is_better": true,
   "tolerance": {"rel": 0.02}, "source": "Table 3"}
]
```

`tolerance` is either `{"abs": x}` or `{"rel": x}`. If the paper reports a std, prefer `{"abs": 2 * std}`.

## Run record — `results/runs.jsonl`

One JSON object per line, appended and never rewritten. Full schema: `bench-setup/references/results-schema.md`. Required keys: `run_id`, `timestamp`, `role`, `method`, `dataset`, `split`, `seed`, `config_path`, `config_hash`, `git_commit`, `git_dirty`, `budget`, `status`, `metrics`.

`role` is one of `repro_baseline`, `baseline`, `extension`, `ablation`, `smoke`.

## Stage 6 — `summary.md`

Every claim is one bullet with the numbers (mean ± std, n seeds), the figure path and the run-id filter or config that produced it. Include a **Where it does not help** section; it may be empty only if all settings improved.

## STATUS.md and workflow state

The block between `<!-- poc-state:begin -->` and `<!-- poc-state:end -->` is generated by `poc_state.py`; don't edit it. Completion verdicts are `passed`, `accepted-with-caveats` or `failed`. Stage statuses (`pending`, `in_progress`, `stale`, `reopened`, `edited`, `awaiting_approval`, `failed`, `done`) are computed; see `references/workflow.md`.

## Reviews — `reviews/<stage>-<run>.md`

Written by stage-critic only, from its template: rubric answers in order, located objections graded blocker / major / minor, the rebuttal of the stage's central claim, a verdict (`pass`, `revise`, `block`) and a meta-review. The verdict is recorded with `poc_state.py review`; `complete` is refused on `block` and `approve` is refused without a review of the current output.

Every handoff file keeps a short **Change log** section at its end (date, trigger, change), so update-mode re-runs leave a trail inside the file as well as in `.poc/events.jsonl`.
