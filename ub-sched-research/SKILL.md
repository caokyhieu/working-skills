# UB Scheduler Research

Answer one question well: **how should YARN, Spark and Flink schedule work when UnifiedBus lets one task use CPU, memory and NPUs spread over several Matrix Servers, and what exactly would have to change in each engine?**

Two ideas hold the skill together:

1. **Placement, ownership and access are different things** [ontology.md §1, O1–O3]. `MatrixServer` is the physical and topological unit; `Resource` and `ResourceComposition` are what gets allocated; `canAccess via UBPath` carries the cost of using a resource that sits elsewhere. Topology still matters under UB; it becomes a cost, not a boundary.
2. **The engines keep their own design** [engines.md, O7]. YARN, Spark and Flink each keep their own ontology, scheduling levels and plugin points. The UB ontology is the common layer for comparing them. Every idea says which engine component carries it, at which level (cluster / application / task), and whether it needs a plugin, a protocol change or a fork. Classic container / executor / slot scheduling is the **degenerate** case of a composition on one server; the research lives in the crosswalk rows marked `lossy` or `none`.

Rules from [research-poc/references/thinking-models.md](../research-poc/references/thinking-models.md) are cited as `[TM-n]`; ontology invariants as `[O-n]`.

## Workspace

```text
ub-sched/
  ontology.md          # living UB ontology (seeded from references/ontology.md; user-confirmed; change log)
  engines.md           # living engine ontologies + crosswalk (seeded from references/engines.md)
  facts.md             # facts register: UB hardware, Matrix Server, engine versions — every number cited [O6]
  questions.md         # research questions and hypotheses (templates/questions.md)
  cards/<source-id>.md # one ontology card per paper, repo, doc or code module (templates/ontology-card.md)
  designs/<name>.md    # scheduler design sketches (templates/design-sketch.md)
  matrix.md            # generated by ub_sched.py matrix
```

Create it with `python <skill-dir>/scripts/ub_sched.py init` (existing files are kept). Place `ub-sched/` at the workspace root next to `research-map.md` when the research-poc workflow is in use.

## 1. Set up (first run)

1. `ub_sched.py init`.
2. Walk the user through `ontology.md` §1–§4 and `engines.md` §4–§5. Ask what they would add, rename or drop; apply confirmed changes and log them. Mark the ontology `confirmed YYYY-MM-DD` at the top.
3. Fill `facts.md` § Engines: which YARN / Hadoop, Spark and Flink versions the team targets, and how they are deployed (Spark and Flink on YARN? Kubernetes?). All engine claims are checked against these versions.
4. Fill what the user knows about their Matrix Servers and UB setup (F5–F9) and mark each row `internal` or `public`. Leave unknowns `UNKNOWN`; don't fill hardware numbers from memory or from marketing copy without a source.
5. Seed `questions.md` from [references/research-lens.md §4](references/research-lens.md). Ask which binding constraint is real today (fragmentation, shuffle / state I/O, or the engines' vocabulary) and order the questions by it.
6. If `research-map.md` exists or is being built, offer to draft its UB scheduling problem block from research-lens.md §1–§3 (formulation, bridging concepts, candidate anchors). The **research-map** skill owns that file and the user confirms the block there.

## 2. Map a source → ontology card

For a paper, repo, blog post or engine document:

1. If a source-digest exists (`sources/<id>/digest.md`), read it and link it in `digest:`; if the source is substantial and has no digest, suggest running **source-digest** first, which records the benchmark protocol and results in detail. The card is the ontology lens on top of it, not a replacement.
2. Read the full source. Fill [templates/ontology-card.md](templates/ontology-card.md) to `ub-sched/cards/<source-id>.md`:
   - **§1 Mapping:** every scheduling-relevant term in the source → UB class or relation, plus the engine term when the source is about an engine, with a fidelity label. Use the source's words in the first column.
   - **§2 Three relations:** say which of placement / allocation / access the source actually models. Most node-local work collapses all three into "runs on node N"; record that as `separates: no`, it isn't a defect of the card.
   - **§3 Engine landing:** level, pattern (A cluster only / B engine only / C co-designed, engines.md §4), components touched, protocol changes, and whether the engine's semantics survive. For engine-agnostic papers, say where the mechanism *would* land and mark it `[inference]`.
   - **§4 Assumptions and transfer:** list assumptions (stated and found), each with a UB verdict that cites `facts.md`, or `unknown` when the needed fact is open. Open facts become rows in `facts.md`.
   - **§5 Cost vector:** one concrete decision in ontology terms, with each dimension `measured`, `modelled` or `UNKNOWN` [O5].
3. Use only terms that exist in `ontology.md` and `engines.md` in the front matter. When a source needs a new term, propose it in §8 and ask; don't add it silently (ontology.md §7).
4. Run `ub_sched.py check` and fix what it reports.

Tag claims as source-digest does: `[src §x / Table y]`, `[code: path@commit]`, `[doc: url, version]`, `[inference]`.

## 3. Read engine code → seam card

When the user points at YARN, Spark or Flink code (or asks "where would this go in Spark?"):

1. Confirm the version from `facts.md`; check out or browse that tag.
2. Start from the engine's section in `engines.md`, follow the named components into the code, and write a `type: code` card with **§7 Seams** filled: class and file at a commit, its role, the node-local assumption it encodes (quote the line), and whether it could carry a UB mechanism without a fork.
3. When the code contradicts engines.md (renamed class, removed API, different default), fix the workspace `engines.md`, log the change, and note it in the card. Code at the target version beats this skill's description.

## 4. Synthesise → matrix, gaps, questions

1. `ub_sched.py matrix` writes `matrix.md`: sources × layers, locality model, whether the three relations are separated, UB transfer verdict; UB concepts no card covers; crosswalk rows (`degenerate` / `lossy` / `none`) with the cards that touch them.
2. Read the matrix with the user. Update `questions.md`: evidence per question, the remaining gap, and a Toulmin-form hypothesis with a kill test [TM-6]. Questions are anchored to crosswalk rows; a question that touches no row is either engine-agnostic (say so) or not yet understood.
3. Point out the thin spots: layers with no evidence, questions whose only evidence is `claim-only`, hardware facts still `UNKNOWN` that decide a transfer verdict.

## 5. Sketch a scheduler design

When the user wants to design something, write `ub-sched/designs/<name>.md` from [templates/design-sketch.md](templates/design-sketch.md):

- State the decision in ontology terms (the SchedulingDecision tree), the cost-vector trade-off, and the closest prior algorithm (with its card).
- **Land it** at each level: YARN component, Spark / Flink component, change type (config / plugin / protocol / fork), and whether unchanged applications still run. Prefer plugin points listed in engines.md; justify every fork.
- Run the **engine fidelity check**: stage / slot / container semantics, failure and recovery with cross-server compositions, queue fairness, dynamic allocation and adaptive scheduling.
- Hand off: a confirmed sketch goes to **idea-extension** (novelty loop, Heilmeier) and **bench-setup** (tuned node-local baseline first, then the design), inside a research-poc idea if the user wants the full workflow.

## 6. Answer questions

For questions like "does anyone schedule Spark on pooled memory?" or "what breaks in Flink slots under UB?", answer from the cards, matrix and crosswalk in ontology and engine terms, cite card ids, and say which parts are not covered by any card. Offer to scout (**source-scout**) or card a source to close the gap rather than answering from memory.

## Rules

- Keep each engine's vocabulary. Write `Spark:Executor`, not "compute node"; map it in the crosswalk instead of renaming it.
- No hardware number without a `facts.md` row that cites a source [O6]. No engine API claim without a version.
- `internal` facts (Matrix Server specs, internal roadmaps, unpublished measurements) never go into search queries, public cards or anything shared outside the team; mark cards that use them `visibility: internal` in their front matter.
- Every mechanism names its level and engine landing [O7]; one that bypasses the engines is labelled a thought experiment.
- Change the ontology only with the user, with a reason and a change-log line; retire terms rather than deleting them.
- Don't rank designs by feel. Compare them with the cost vector and the hypotheses' kill tests; use pairwise comparison when choosing between sketches [TM-9].
